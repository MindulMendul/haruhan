# Event Loop

## 한 줄 정의

JS 엔진이 **단일 콜 스택**으로 코드를 실행하면서, 비동기 작업을 **태스크 큐/마이크로태스크 큐**로 스케줄링해 넘겨받는 실행 모델.

## 카드 요약

- **콜 스택**: 지금 실행 중인 함수 호출들이 쌓이는 자료구조. 동기 코드는 여기서만 처리된다.
- **태스크 큐(매크로태스크)**: `setTimeout`, I/O, 이벤트 콜백 등이 대기하는 큐.
- **마이크로태스크 큐**: `Promise`, `queueMicrotask`, `MutationObserver` 콜백이 대기하는 큐. 매크로태스크보다 항상 먼저 비운다.
- **렌더링**: 브라우저는 한 매크로태스크가 끝나고 마이크로태스크 큐를 모두 비운 다음, 필요하면 렌더링을 한 번 끼워 넣는다.

## 실행 순서 원칙

이벤트 루프의 한 사이클은 대략 아래 순서로 돈다.

1. 콜 스택이 빌 때까지 동기 코드를 실행한다.
2. 콜 스택이 비면 **마이크로태스크 큐를 큐가 빌 때까지 전부** 실행한다. (실행 중 추가된 마이크로태스크도 같은 사이클에서 처리)
3. 마이크로태스크 큐가 비면, 필요 시 브라우저가 렌더링(스타일 계산, 레이아웃, 페인트)을 수행한다.
4. 태스크 큐에서 매크로태스크를 **하나만** 꺼내 실행한다.
5. 다시 2번으로 돌아간다.

이 규칙 때문에 `setTimeout(fn, 0)`은 "즉시 실행"이 아니라 "현재 스택과 모든 마이크로태스크가 끝난 뒤 실행"을 의미한다.

## 마이크로태스크 vs 매크로태스크

| | 마이크로태스크 | 매크로태스크(태스크) |
|--|--|--|
| **대표 예시** | `Promise.then/catch/finally`, `async/await`의 이후 코드, `queueMicrotask` | `setTimeout`, `setInterval`, I/O 콜백, UI 이벤트 |
| **처리 시점** | 콜 스택이 빌 때마다, 큐가 빌 때까지 전부 | 한 사이클에 하나씩 |
| **렌더링과의 관계** | 렌더링 전에 항상 먼저 처리 | 렌더링 뒤에 처리될 수 있음 |
| **위험** | 마이크로태스크 안에서 계속 새 마이크로태스크를 만들면 렌더링이 무한정 지연될 수 있다 | 큐가 밀리면 지연 시간이 늘어난다 |

```
console.log("1");
setTimeout(() => console.log("2 (macrotask)"), 0);
Promise.resolve().then(() => console.log("3 (microtask)"));
console.log("4");
// 출력 순서: 1 -> 4 -> 3 -> 2
```

## async/await는 무엇을 감추고 있나

`async` 함수는 항상 Promise를 반환하고, `await` 뒤의 코드는 사실상 `.then()` 콜백과 같다. 즉 `await`를 만나는 순간 함수 실행이 잠깐 멈추고, 남은 부분은 **마이크로태스크**로 스케줄링된다. 그래서 아래 두 코드는 동작이 동일하다.

```
async function f() {
  console.log("a");
  await Promise.resolve();
  console.log("b");
}
```

```
function f() {
  console.log("a");
  return Promise.resolve().then(() => console.log("b"));
}
```

면접에서는 "`await`가 코드를 멈추는 것처럼 보이지만, 사실은 이후 로직을 마이크로태스크로 미루는 문법 설탕"이라고 설명하면 이해도가 잘 드러난다.

## 브라우저 vs Node.js

- **브라우저**: 태스크 큐가 하나이며, 마이크로태스크 처리 후 렌더링 여부를 판단한다. `requestAnimationFrame`은 렌더링 직전에, `requestIdleCallback`은 유휴 시간에 실행된다.
- **Node.js**: 이벤트 루프에 **timers → pending callbacks → poll → check → close callbacks**로 이어지는 여러 단계(phase)가 있고, 각 단계 사이마다 마이크로태스크 큐(Promise)와 `process.nextTick` 큐를 비운다. `process.nextTick`은 일반 마이크로태스크보다도 우선순위가 높다.
- 두 환경 모두 "동기 코드 → 마이크로태스크 전부 → 매크로태스크 하나"라는 큰 틀은 같지만, 매크로태스크의 종류와 단계 구성이 다르다.

## 실무에서 자주 겪는 문제

- **긴 동기 작업으로 인한 UI 멈춤**: 콜 스택을 오래 붙잡는 반복문/무거운 계산은 렌더링과 사용자 입력 처리를 막는다. `setTimeout`으로 쪼개거나 Web Worker로 옮겨서 완화한다.
- **마이크로태스크 폭주**: `then` 체인이나 재귀적인 Promise 생성이 계속 마이크로태스크를 만들면, 매크로태스크(타이머, 렌더링)가 계속 밀릴 수 있다.
- **타이머 지연 오해**: `setTimeout(fn, 1000)`은 "정확히 1초 뒤"가 아니라 "최소 1초 뒤, 콜 스택이 비어야 실행"이다. 메인 스레드가 바쁘면 더 늦게 실행된다.

## 대표 질문

- "`setTimeout(fn, 0)`은 왜 바로 실행되지 않나요?"
- "Promise와 setTimeout을 같이 쓰면 실행 순서는 어떻게 되나요?"
- "`async/await`는 내부적으로 어떻게 동작하나요?"
- "브라우저와 Node.js의 이벤트 루프는 어떻게 다른가요?"
- "무거운 연산이 UI를 멈추게 하면 어떻게 대응하나요?"

## 면접 포인트

1. **큐를 구분해서 말한다**: 마이크로태스크와 매크로태스크를 뭉뚱그리지 말고, 우선순위 차이를 명확히 짚는다.
2. **코드로 순서를 검증한다**: 실행 순서를 묻는 문제는 콜 스택 → 마이크로태스크 → 매크로태스크 흐름을 단계별로 짚으며 답한다.
3. **"단일 스레드"의 의미를 정확히**: JS 실행은 단일 스레드지만, I/O나 타이머는 브라우저/OS가 처리하고 콜백만 큐로 돌아온다는 점을 설명한다.
4. **실무 임팩트 연결**: 이벤트 루프 이해가 부족하면 생기는 실제 버그(순서 오해로 인한 레이스 컨디션, UI 프리징)를 예시로 든다.

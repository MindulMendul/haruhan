# CSR & SSR

## 한 줄 정의

**CSR**은 브라우저에서 JS가 DOM을 그리고, **SSR**은 서버가 요청마다 완성된 HTML을 만들어 내려보낸다. 여기에 빌드 시점에 미리 만드는 **SSG**, 주기적으로 다시 만드는 **ISR**, 서버 컴포넌트를 조각내 스트리밍하는 방식까지가 렌더링 전략의 스펙트럼이다.

## 카드 요약

| | CSR | SSR | SSG | ISR |
|--|--|--|--|--|
| **HTML 생성 시점** | 클라이언트(런타임) | 요청마다(런타임) | 빌드 시점 | 빌드 + 주기적 재생성 |
| **첫 화면 콘텐츠** | JS 실행 후 | 응답에 이미 포함 | 응답에 이미 포함 | 응답에 이미 포함 |
| **SEO** | 추가 대응 필요 | 유리 | 유리 | 유리 |
| **서버 부하** | 낮음(정적 파일만) | 요청마다 렌더 비용 | 없음(캐시된 정적 파일) | 낮음(재생성 주기 외에는 정적) |
| **데이터 신선도** | 항상 최신(클라이언트 fetch) | 항상 최신 | 빌드 시점 데이터로 고정 | 주기적으로만 갱신 |

## 언제 무엇을 고르나

- **CSR**: 대시보드, 관리자 페이지처럼 로그인 뒤 개인화된 화면이고 SEO가 필요 없으며, 이후 상호작용(페이지 전환)이 빈번한 경우.
- **SSR**: 상품 상세, 뉴스처럼 요청마다 데이터가 달라지고 SEO와 빠른 첫 콘텐츠 노출(FCP)이 동시에 중요한 경우.
- **SSG**: 블로그, 마케팅 랜딩처럼 콘텐츠가 자주 바뀌지 않는 경우. 서버 렌더 비용이 없어 가장 빠르고 저렴하다.
- **ISR**: 상품 목록처럼 데이터가 바뀌긴 하지만 초 단위 실시간성까진 필요 없는 경우. "정적인 속도 + 주기적 최신화"를 동시에 노린다.

## 하이드레이션(Hydration)이란

SSR/SSG는 서버가 만든 HTML을 먼저 보여주지만, 그 HTML에는 아직 이벤트 핸들러가 붙어 있지 않다. 브라우저가 같은 JS 번들을 다운로드해 **React 트리를 다시 계산하고, 서버가 만든 DOM에 이벤트 리스너를 붙이는 과정**이 하이드레이션이다.

- 하이드레이션이 끝나기 전까지는 화면은 보이지만 클릭 등 상호작용이 반응하지 않을 수 있다(TTI와 FCP의 격차).
- 서버에서 렌더링한 결과와 클라이언트에서 다시 계산한 결과가 다르면 **하이드레이션 불일치(mismatch)** 경고가 발생한다.

### 하이드레이션 불일치의 대표 원인

1. **서버/클라이언트에서 값이 다른 API를 쓴 경우**: `Date.now()`, `Math.random()`, `window` 접근처럼 서버와 브라우저에서 결과가 달라지는 값을 렌더링에 직접 사용.
2. **조건부 렌더링이 환경에 따라 갈리는 경우**: 로그인 여부를 로컬 스토리지에서 읽어 조건부로 그리면, 서버는 항상 "비로그인" 버전을, 클라이언트는 "로그인" 버전을 그려 불일치가 생긴다.
3. **타임존/로케일 차이**: 서버와 클라이언트의 시간대가 다르면 날짜 포맷 결과가 달라질 수 있다.

**디버깅 접근**: 브라우저 콘솔의 hydration 경고가 가리키는 컴포넌트부터 확인하고, "이 값이 서버와 클라이언트에서 정말 같은가"를 하나씩 좁혀간다. 환경 의존적인 값은 `useEffect` 안에서 클라이언트 전용으로 세팅하거나, 서버에서도 동일한 값을 계산해 내려주는 방식으로 맞춘다.

## React Server Components와 스트리밍 SSR

Next.js App Router 이후로는 SSR을 "한 번에 전체 HTML을 만들어 보낸다"가 아니라 **조각내서 스트리밍**하는 방식이 기본이 되었다.

- **서버 컴포넌트(RSC)**: 서버에서만 실행되고 클라이언트 번들에 포함되지 않는 컴포넌트. 데이터 fetch를 컴포넌트 트리 가까이서 바로 할 수 있어 워터폴을 줄이고, JS 번들 크기를 줄인다.
- **클라이언트 컴포넌트**: `"use client"`로 표시하며, 상호작용(이벤트 핸들러, 상태)이 필요한 부분만 여기 둔다.
- **스트리밍**: 페이지 전체가 준비될 때까지 기다리지 않고, 준비된 부분부터 `<Suspense>` 경계 단위로 먼저 내려보낸다. TTFB를 낮추고, 느린 데이터 소스가 있어도 나머지 화면을 먼저 보여줄 수 있다.

이 구조에서는 "서버 컴포넌트는 항상 최신 데이터를 서버에서 그리고, 클라이언트 컴포넌트만 하이드레이션 대상이 된다"는 점이 CSR/SSR 논의를 한 단계 더 세분화한다.

## 실무 포인트

- SEO와 초기 로딩이 중요한 페이지와, 로그인 뒤 개인화된 페이지를 같은 전략으로 묶지 말고 라우트 단위로 전략을 나눈다.
- ISR의 재생성 주기는 "데이터가 얼마나 자주 바뀌는가"와 "약간 오래된 데이터를 보여줘도 괜찮은가"를 함께 판단해서 정한다.
- 스트리밍 SSR을 쓸 때는 느린 데이터에 의존하는 컴포넌트를 `<Suspense>`로 감싸, 나머지 UI가 그 컴포넌트 때문에 전체적으로 지연되지 않게 한다.

## 대표 질문

- "CSR과 SSR 중 어떤 상황에서 무엇을 선택하나요?"
- "SSG와 ISR은 어떻게 다른가요?"
- "하이드레이션이 무엇이고, 하이드레이션 불일치는 왜 생기나요?"
- "React Server Components는 기존 SSR과 무엇이 다른가요?"
- "스트리밍 SSR이 TTFB/LCP에 어떤 영향을 주나요?"

## 면접 포인트

1. **표로 비교하지 말고 기준으로 말한다**: CSR/SSR/SSG/ISR을 나열만 하지 말고, "이 페이지는 이래서 이 전략"이라는 판단 기준을 붙인다.
2. **하이드레이션을 구체적으로 설명한다**: "서버 HTML + 클라이언트 JS가 만나 이벤트를 붙이는 과정"이라고 정의한 뒤, 불일치 원인을 예시로 든다.
3. **RSC를 최신 트렌드로 언급한다**: 서버/클라이언트 컴포넌트 구분과 스트리밍까지 설명하면 최신 아키텍처 이해도를 보여줄 수 있다.
4. **트레이드오프를 숨기지 않는다**: SSR은 서버 비용이 늘고, SSG/ISR은 데이터 신선도를 일부 포기한다는 점을 함께 말한다.

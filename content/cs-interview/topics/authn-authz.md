# Authorization & Authentication

## 한 줄 정의

**인증(Authentication)**은 "누구인지 확인하는 것", **인가(Authorization)**는 "확인된 사용자가 무엇을 할 수 있는지 결정하는 것"이다. 이 둘을 구분하지 못하면 보안 설계 전체가 흔들린다.

## 카드 요약

- **인증**: 로그인, 비밀번호/OTP/생체인증, 세션·토큰 발급까지의 과정.
- **인가**: 로그인 이후 "이 리소스에 접근 가능한가"를 역할(role)/권한(permission)으로 판단하는 과정.
- **세션 vs 토큰**: 서버가 상태를 들고 있는 방식(세션) vs 클라이언트가 서명된 정보를 들고 있는 방식(JWT 등 토큰).
- **프론트는 UX, 서버는 보안**: 버튼을 숨기는 건 사용자 경험일 뿐, 실제 권한 검증은 반드시 서버(API)에서 다시 한다.

## 세션 기반 인증 vs 토큰 기반 인증

### 세션 기반
1. 로그인 성공 시 서버가 세션을 생성하고 세션 ID를 쿠키로 내려준다.
2. 서버(또는 세션 스토어, Redis 등)가 세션 ID ↔ 사용자 정보를 들고 있는다.
3. 이후 요청마다 쿠키의 세션 ID로 서버가 사용자를 조회한다.
4. 로그아웃/강제 만료가 서버에서 즉시 가능하다(세션 삭제).

### 토큰 기반(JWT 등)
1. 로그인 성공 시 서버가 사용자 정보를 담아 서명한 토큰(Access Token)을 발급한다.
2. 클라이언트는 이후 요청마다 토큰을 헤더(`Authorization: Bearer ...`)로 보낸다.
3. 서버는 별도 조회 없이 **서명 검증만으로** 토큰 내용을 신뢰할 수 있어 수평 확장에 유리하다(stateless).
4. 대신 발급된 토큰은 만료 전까지 서버가 강제로 무효화하기 어렵다는 단점이 있다.

## Access Token / Refresh Token 패턴

Access Token만 계속 쓰면, 탈취당했을 때 만료 전까지 계속 악용될 수 있다. 그래서 실무에서는 보통 아래처럼 이원화한다.

- **Access Token**: 수명이 짧다(예: 5~30분). API 요청마다 사용.
- **Refresh Token**: 수명이 길다(예: 며칠~몇 주). Access Token이 만료되면 이걸로 새 Access Token을 재발급받는 데만 사용.
- **Refresh Token Rotation**: Refresh Token을 쓸 때마다 새 Refresh Token으로 교체하고 이전 것은 즉시 폐기한다. 탈취된 옛 토큰이 재사용되면(재사용 탐지) 그 사용자의 모든 토큰 체인을 무효화해 탈취 피해를 최소화한다.

이 패턴 덕분에 Access Token이 짧게 노출돼도 피해 범위가 제한되고, 사용자는 매번 로그인하지 않아도 세션이 자연스럽게 이어진다.

## 토큰 저장 위치와 위협 모델

| 저장 위치 | XSS 위험 | CSRF 위험 | 비고 |
|--|--|--|--|
| **LocalStorage** | JS로 직접 접근 가능해 위험 | 자동 전송 안 되어 CSRF엔 안전 | XSS 한 방으로 토큰 탈취 가능 |
| **일반 Cookie** | JS로 접근 가능(HttpOnly 아니면) | 요청에 자동 포함되어 CSRF 위험 | |
| **HttpOnly + Secure + SameSite Cookie** | JS 접근 불가(XSS로도 못 읽음) | SameSite 설정으로 크게 완화 | 가장 널리 권장되는 조합 |

정답은 하나로 정해져 있지 않지만, "XSS를 막을 자신이 있는가", "CSRF 대응(SameSite, CSRF 토큰)을 같이 할 수 있는가"를 놓고 위협 모델 기준으로 선택하는 것이 실무적인 답변이다.

## OAuth2 / OIDC 흐름 (Authorization Code + PKCE)

OAuth2는 "제3자 서비스에 내 자격증명을 직접 주지 않고, 권한만 위임"하기 위한 프로토콜이고, OIDC(OpenID Connect)는 그 위에 "이 사용자가 누구인지"까지 표준화한 인증 계층이다.

1. 사용자가 "구글로 로그인"을 누르면, 앱은 사용자를 구글 인가 서버로 리다이렉트한다.
2. 사용자가 구글에서 로그인/동의하면, 구글은 **Authorization Code**를 앱의 콜백 URL로 돌려준다.
3. 앱의 백엔드(또는 PKCE를 쓰는 SPA)가 이 코드를 구글 토큰 엔드포인트에 보내 **Access Token/ID Token**으로 교환한다.
4. ID Token(OIDC)에는 사용자 식별 정보가 담겨 있어, 이걸로 로그인 사용자를 특정한다.

SPA처럼 클라이언트 시크릿을 안전하게 보관할 수 없는 환경에서는 **PKCE(Proof Key for Code Exchange)**를 추가해, 코드가 가로채이더라도 검증 코드(code_verifier) 없이는 토큰 교환이 불가능하게 만든다.

## 대표 웹 취약점과 방어

- **XSS**: 신뢰할 수 없는 스크립트가 실행되는 문제. 출력 이스케이프, `Content-Security-Policy`, 사용자 입력 검증/정제로 줄인다.
- **CSRF**: 사용자의 인증 상태(쿠키)를 이용해 원치 않는 요청을 보내는 문제. `SameSite=Lax/Strict` 쿠키, CSRF 토큰 검증으로 방어한다.
- **권한 상승(Broken Access Control)**: 인증은 됐지만 인가 검증이 빠진 경우. "로그인했다"와 "이 리소스에 접근 가능하다"를 항상 서버에서 별도로 검증해야 한다.

## 실무 포인트

- 프론트에서 역할에 따라 메뉴/버튼을 숨기는 건 UX 개선일 뿐, 그 API를 직접 호출하면 서버가 다시 막아야 진짜 보안이다.
- 토큰 만료 시간은 "짧을수록 안전, 길수록 편리"라는 트레이드오프이며, Refresh Token Rotation으로 그 간극을 좁힌다.
- 다중 기기 로그아웃, 강제 세션 종료가 필요한 서비스는 완전한 stateless JWT보다 세션(또는 토큰 블랙리스트/화이트리스트 관리)이 더 다루기 쉬울 수 있다.

- "JWT를 어디에 저장해야 안전한가요?"

- "CSRF와 XSS는 각각 무엇을 노리고, 어떻게 방어하나요?"

## 면접 포인트

1. **정의부터 명확히**: 인증/인가를 한 문장씩 구분해서 시작하면 이후 설명이 깔끔해진다.
2. **트레이드오프를 짚는다**: 세션 vs 토큰, 토큰 저장 위치 모두 "정답"이 아니라 위협 모델에 따른 선택이라는 점을 강조한다.
3. **재발급/폐기 흐름까지 말한다**: 로그인 성공만 설명하지 말고, 만료·재발급·강제 로그아웃까지 다루면 실무 경험이 드러난다.
4. **서버 검증을 반드시 언급한다**: 프론트 권한 처리는 UX이고, 실제 보안은 서버 인가 검증이라는 원칙을 빼먹지 않는다.

# State Management

## 한 줄 정의

애플리케이션의 상태를 **어디에, 어떤 범위로, 어떻게 동기화**할지 결정하는 설계 영역. "무엇으로 관리하느냐"보다 "어떤 종류의 상태인가"를 먼저 구분하는 것이 핵심이다.

## 카드 요약

- **상태의 종류**: 로컬 상태, 전역 클라이언트 상태, 서버 상태, URL 상태는 서로 성격이 달라 같은 도구로 풀면 안 된다.
- **범위가 먼저, 도구는 나중**: 몇 개 컴포넌트가 공유하는지, 얼마나 자주 바뀌는지가 도구 선택 기준이다.
- **서버 상태는 별도 취급**: 캐싱, 재검증, 로딩/에러 상태가 필요해 React Query/SWR 같은 전용 도구가 유리하다.
- **URL도 상태 저장소다**: 필터, 페이지, 탭 같은 값은 새로고침/공유가 필요하면 URL(쿼리 파라미터)에 두는 게 자연스럽다.

## 상태의 네 가지 종류

### 1. 로컬(컴포넌트) 상태
하나의 컴포넌트, 혹은 부모-자식 몇 단계 안에서만 쓰이는 상태. `useState`/`useReducer`로 충분하며, 굳이 전역으로 끌어올릴 필요가 없다.

### 2. 전역 클라이언트 상태
로그인 여부, 테마, 열려 있는 모달처럼 앱 여러 곳에서 읽고 쓰는 UI 상태. Context, Redux, Zustand, Recoil 같은 전역 스토어가 필요해지는 지점이다.

### 3. 서버 상태(Server State)
서버가 원본(source of truth)을 가지고 있는 데이터(목록, 상세, 프로필 등). 클라이언트는 이걸 **캐시**해서 보여줄 뿐이라, 일반 전역 상태 도구로 관리하면 로딩/에러/재요청/캐시 무효화를 전부 직접 구현해야 한다.

### 4. URL 상태
검색어, 필터, 페이지 번호, 선택된 탭처럼 "새로고침해도 유지되고, 링크로 공유돼야 하는" 값. 쿼리 파라미터나 라우트 세그먼트로 표현하면 별도 상태 없이 브라우저 히스토리가 상태를 대신 관리해준다.

## 전역 상태 도구 비교

| | Context API | Redux(Toolkit) | Zustand | Recoil/Jotai |
|--|--|--|--|--|
| **러닝 커브** | 낮음(내장) | 높음(보일러플레이트) | 낮음 | 낮음~중간 |
| **리렌더 최적화** | 기본적으로 취약(값이 바뀌면 모든 구독 컴포넌트 리렌더) | selector로 세밀 제어 가능 | selector 기반, 기본적으로 세밀 | atom 단위라 세밀 |
| **적합한 규모** | 자주 안 바뀌는 소규모 전역값(테마, 인증 등) | 대규모, 복잡한 상태 전이/미들웨어 필요 시 | 중소~중대 규모, 빠른 도입 | atom 단위 세분화가 필요한 경우 |
| **미들웨어/디버깅** | 없음 | Redux DevTools, 미들웨어 생태계 풍부 | 가능(devtools, persist 등 플러그인) | 제한적 |

**선택 기준 요약**: 값이 드물게 바뀌고 구조가 단순하면 Context, 상태 전이가 복잡하고 팀 규모가 크면 Redux, 빠르게 도입하고 보일러플레이트를 줄이고 싶으면 Zustand, 세분화된 원자 단위 구독이 필요하면 Recoil/Jotai 계열을 고려한다.

## 서버 상태를 별도로 다뤄야 하는 이유

React Query(TanStack Query)나 SWR 같은 도구는 아래를 기본으로 제공한다.

- **캐싱과 재사용**: 같은 쿼리 키로 요청하면 캐시를 즉시 보여주고 백그라운드에서 갱신(stale-while-revalidate).
- **로딩/에러 상태 자동 관리**: `isLoading`, `isError`를 매번 직접 만들 필요가 없다.
- **재검증 전략**: 포커스 복귀, 재연결, polling 등 다양한 트리거로 최신화한다.
- **낙관적 업데이트(optimistic update)**: 뮤테이션 성공을 가정하고 먼저 UI를 갱신한 뒤, 실패 시 롤백한다.

전역 상태 스토어(Redux/Zustand)에 서버에서 받아온 데이터를 그대로 넣고 직접 캐시 무효화 로직을 짜면, 결국 React Query가 이미 해결한 문제를 재구현하게 된다. 그래서 실무에서는 **"클라이언트 UI 상태는 Zustand/Redux, 서버 상태는 React Query"** 식으로 역할을 나누는 경우가 많다.

## 전역 상태를 도입하는 기준

1. **얼마나 많은 컴포넌트가 공유하는가**: 2~3단계 props drilling 정도면 아직 전역화가 급하지 않을 수 있다.
2. **변경 빈도와 리렌더 비용**: 자주 바뀌는 값을 최적화 없이 Context에 두면 하위 트리 전체가 리렌더된다.
3. **상태의 출처**: 서버 데이터인지, 순수 클라이언트 UI 상태인지, URL로 표현 가능한지부터 구분한다.
4. **팀/코드베이스 규모**: 도구가 늘어날수록 학습 비용과 유지보수 비용이 커지므로, 꼭 필요한 만큼만 도입한다.

## 대표 질문

- "전역 상태를 도입해야 하는 기준은 무엇인가요?"
- "서버 상태와 클라이언트 상태를 왜 구분해서 관리하나요?"
- "Redux와 Zustand 중 어떤 상황에 무엇을 선택하나요?"
- "Context API를 상태 관리에 쓸 때 어떤 성능 문제가 생길 수 있나요?"
- "URL을 상태 저장소로 쓰는 것의 장점은 무엇인가요?"

## 면접 포인트

1. **도구보다 상태 종류를 먼저 말한다**: "무슨 라이브러리를 쓰나요"보다 "어떤 상태인가"를 먼저 구분하는 답변이 더 좋은 인상을 준다.
2. **리렌더링 비용을 안다**: Context의 구독 전체 리렌더 문제, selector 기반 최적화의 필요성을 구체적으로 설명한다.
3. **서버 상태를 별도로 취급하는 이유를 설명한다**: 캐싱/재검증/로딩 상태를 직접 구현하는 것과 React Query를 쓰는 것의 차이를 비교한다.
4. **과설계를 경계한다**: "일단 Redux부터 깐다"가 아니라 필요할 때 점진적으로 도입한다는 실무 감각을 보여준다.
